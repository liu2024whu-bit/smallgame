## 1. 项目身份：先保住它为什么值得做

游戏当前名称为《写给第20圈的无地址信》。它是一份面向20岁生日的个人网页解谜礼物，而不是通用生日祝福模板、角色图片展示站或密码题合集。

### 1.1 已恢复的明确要求

- 从初三相识一路走到大学阶段，将回忆与关卡串成一条完整线索，不做互不相关的主题展板。
- 情感表达含蓄、有浪漫主义色彩，以纪念和祝福为核心；不强行表白，不替双方定义关系，结尾保留未来空间。
- 保留 `2006`、`1029`、`LXY`、`BIRTHDAY`、`20岁` 等身份元素。
- 保留光遇两组外观关系：**巫师帽＋正太头、樱花头＋正太头**。它们是玩家造型关系，不是原作固定姓名；不能用几个抽象符号代替具体人物图像。
- 保留魈、散兵／流浪者；鬼灭的水柱、风柱、蛇柱等角色；带土、卡卡西；小王子与玫瑰；武汉大学、南京大学；猫、狗、鲜花。
- 参考《绣湖》的探索与多步机关体验，以及《拣爱》方向的画作质感和情绪表达。参考的是体验目标，不直接复制原作关卡、构图与资源。
- 画面不能靠矢量图形、CSS几何块和符号堆成“假插画”；角色、花卉和道具必须有具体、统一的视觉素材。允许必要的文字、按钮、热点边界和界面图标由代码实现，但它们不能替代场景美术。
- 图片必须裁切干净、光照与尺度协调，不能遮住谜面、操作区或重要内容；不要把一批图片装进大小不一的方框就当作美术完成。
- 谜题要比简单排序、直接输入生日更有深度，逻辑公平、玩法多样，不靠无提示穷举增加难度。
- 动画、音效和章节过渡要与玩法共同设计；代码保持分层，旧版本保留，不反复在主分支堆补丁。

### 1.2 信息真实性边界

仓库目前把原神放在高中章节、鬼灭放在大一、带土与卡卡西放在大二、双城放在大三。下表恢复的是**现有实现的分配**，不代表所有真实经历的时间已被核实。后续不得据此编造某年某月发生过的具体对话、旅行、见面或承诺。

新写的房间、暗房、邮局等应明确作为承载记忆的虚构场景，不写成未经提供的真实事件。

### 2.2 本轮代码核对发现的差距

**A. 玩法仍偏向“看图—操作控件—得到答案”。**

多章主要采用排序、点击转盘、年份下拉选择和表单提交。尤其104号底片通过三个布尔状态分别显示L、X、Y；这和字母由画稿上的真实叠片、遮罩或显影效果显现出来，是不同的体验。应把关键观察真正制作进美术与机关状态，而不是只在旁边弹出字母。

**B. 素材仍大量依赖外链。**

`src/assets.js` 引用了图片站、百科、媒体站和学校站点。当前入口函数主要生成带 `loading="lazy"` 的图片标签，并不等于拥有完整的素材预加载、内容核对、失败重试与替代显示机制。本轮没有逐个访问这些图片，不能声称它们目前全部失效或全部可用。

正式版应把确认可使用、可随游戏分发的核心素材收纳到项目中，或使用自己可管理的资源托管；记录来源、许可、用途、裁切和版本，不把“非商业用途”当作已完成授权核对。

**C. 当前版本标识不统一。**

基线提交标题写的是V1.2，`STORY.version` 为1.1.0，`package.json` 为1.0.0。新版应有一个发布版本源，并在调试信息中展示构建提交，避免“打开的还是旧版”无法判断。

**D. 现有语法检查命令存在覆盖盲区。**

`package.json` 使用 `node --check src/*.js`。本轮在独立Node v22.16.0环境中做了最小复现：第一个文件语法正常、第二个文件语法错误时，`node --check a-valid.js b-invalid.js` 返回0，而单独检查第二个文件返回1。不能把这条命令视为逐一检查所有展开文件。

后续应使用一个跨平台脚本遍历目标文件，对每个文件执行 `node --check`，任一失败即整体失败；同时增加“非首个文件损坏也必须报错”的回归测试。这个复现不是对整仓测试的替代。

**E. CI通过不等于画面精致或完整通关。**

本轮读取到的基线CI运行是2026-07-15的成功记录；现有工作流执行 `npm run check` 和 `npm test`。没有据此确认所有外部图片、手机交互、音频和完整浏览器流程都正常。

核对范围：仓库目录、README、核心故事／素材／谜题／章节渲染／存档文件、架构说明、package配置与工作流记录。本轮本地clone因网络域名解析失败，**没有启动整仓、没有重新运行整仓测试、没有浏览器视觉验收、没有生成新版画面**。

## 3. 精修方向：从照片题册改成能探索的记忆空间

### 3.1 建议的整体体验

保留“无地址信、记忆簿、红线、年轮”的共同意象。玩家从一间具体的房间出发，触摸物件、观察局部、打开抽屉、翻看信件，进入不同阶段的记忆；每章留下的不是只有一串密码，还包括可带回来的物件或对旧物的新理解。

建议结构：

`起始房间 → 初三记忆 → 高中风窗 → 大一花房 → 大二暗房 → 大三双城 → 回到起始房间 → 第20圈与生日信`

这里的花房、风窗、暗房等是新版场景提案。主线依然线性，但每章内部允许少量自由调查。结局回到开始的桌面，用已经理解的物件完成最后动作，形成前后呼应。

### 3.2 八个阶段的升级方向（待关卡细化）

| 阶段 | 新版建议 | 避免退回旧问题 |
| --- | --- | --- |
| 起始房间 | 通过纸片、遮挡、高低位置和一个可使用道具理解两张吊牌，打开信封夹层 | 不把两个动物做成并排图片按钮；不直接展示完整读法 |
| 初三 | 将两组光遇搭配制作成有具体人物的记忆物件，通过星图透光片、影子与玫瑰位置复原相识页 | 不做四张卡片上移下移；不把正太和巫师帽当成固定姓名 |
| 高中 | 利用魈、流浪者相关的具体图像与风窗物件，通过遮挡、旋转和光向揭示EAST | 不让人物成为与谜题无关的装饰贴图 |
| 大一 | 用水面倒影、风铃与紫藤遮光构成观察链，角色图像作为场景中的实际作品参与线索 | 不考未提供的动漫百科知识；不重复排序字母片 |
| 大二 | 把三份现有本地作品放进可操作灯箱，使用红片、正负片和局部遮罩真正显现痕迹 | 不只点击热点后凭空弹出LXY |
| 大三 | 两张校园明信片／邮戳通过折叠、背面纹理和对应缺口拼成日期 | 不只转方向按钮；机关方位不冒充真实地理关系 |
| 年轮 | 回收前面保存的年份与物件，完成一个轻量空间拼合，让前后时间线获得解释 | 不在临近结局突然加入高难度全新规则 |
| 生日信 | 亲手整理花、缎带、封蜡和记忆物件，最后打开信 | 不把情绪落点简化成第三次填写同样的密码 |

`1029`、`LXY` 和 `BIRTHDAY` 是情感锚点，不需要承担所有谜题的保密性。玩家即便提前知道生日，也应仍然需要理解场景中的物件关系。

### 3.3 角色与物件怎样自然存在

具体人物可以作为画稿、钥匙扣、相框中的双人合照、桌面立绘或明确属于场景的作品出现；不是一律替换成图标，也不是把不同来源的立绘悬浮贴满画面。

小王子与玫瑰不能只剩“有一张玫瑰照片”。需要在作品／物件层和叙事层都能被辨认出来，并在结尾回收“照料、等待、各自生长”的含蓄主题。

猫狗应参与可理解的小动作，例如视线、位置变化、守着物件；鲜花应是具体花材。每章花种、素材内容与文字要逐一对应，不允许图像是别的植物但alt和标题写成目标花种。

## 4. 第一章样板：先验证一段真正完成的游戏

第一阶段只制作**起始房间的一段完整可玩流程**。暂定目标体验长度为玩家游玩10—15分钟，用试玩修正；这不是开发工期承诺。

### 4.1 样板应该包含什么

一张完整房间主场景、三个有必要的局部观察视图、猫狗的少量状态素材、约六至八个有效调查点、一个可拾取和使用的工具、三个有因果关系的机关、自动存档、分级提示、音效与进入下一章的完整过渡。

控制范围，不为凑数量加入没有作用的抽屉或装饰按钮。

### 4.2 一个可落地的示范链（新增提案）

1. 玩家翻看桌上信件，发现一张带圆孔的索引纸。纸上只有“先高处，后地面”的观察规则，不写最终数字。
2. 观察窗台和桌脚，确认猫与狗所在位置；对两只动物的调查分别让吊牌可被看清，不要求反复乱点。
3. 将索引纸分别放到两个局部视图的定位点。孔位与吊牌上可见标记重合后，得到两个有明确读取方向的片段。
4. 把片段在信封扣上按规则组合，识别2006。数字完整露出之前，仍需获得并正确使用索引纸；不能靠事先知道年份跳过这段物件逻辑。
5. 信封夹层打开，取出第一张完整记忆页和下一章需要的透光片。镜头沿纸上红线进入初三场景。

这个示范仍需把孔位、图形和唯一解画成机关制作稿。不能把“看起来能拼”当作已经验证唯一解。

### 4.3 样板完成的标准

- 主视图像同一个完整空间，不像网页里的图片集合；道具的透视、阴影、尺度一致。
- 点击、近看、拾取、选择、使用、失败反馈、返回主视图全部可用。
- 正确道具未取得时不能凭输入已知答案跳过必需剧情；错误尝试不消耗关键道具、不造成死局。
- 每次操作后的可见状态与存档一致；在每个中间节点刷新都能继续。
- 鼠标、触屏以及必要的键盘操作均可完成。拖动提供“选中道具后点击目标”的替代方式。
- 音效可以关闭；动效可以减弱；跳过过场后仍落到正确游戏状态。
- 浏览器中真实走完流程，并在桌面和手机尺寸留存对照截图；没有上述证据，不标记为完成。

## 5. 美术与动画制作规范

### 5.1 先定整张场景，再拆资源

先完成房间主视图、关键近景、道具特写和至少一个手机布局的协调概念，确认构图后再制作可分离的背景、前景、角色状态和道具图片。不能直接把一张整页设计图作为可点击界面交付。

新制作的主场景建议采用统一的手绘栅格画作质感，纸张、木材、玻璃、花瓣有明确材质。真实照片与现有作品保留内容本身，但通过场景中的相框、纸页、灯箱等方式融入同一光照环境，而不是简单套同一个滤镜。

已有作品不得在未经要求时被擅自改画、裁掉主体或加入并不存在的内容。允许为展示做必要的透明边缘处理、尺寸版本和不破坏作品的展示裁切，并保留来源版本。

### 5.2 最低资产清单

| 类别 | 应记录内容 |
| --- | --- |
| 场景 | 概念稿、主背景、前景遮挡层、局部近景、画面安全区 |
| 道具 | 未获取／已获取／选中／使用后状态，物件锚点与透明边缘 |
| 角色和动物 | 明确身份、视线／姿态状态、尺寸、遮挡关系 |
| 文本和机关 | 可读文字由界面渲染；对解题重要的画内数字与记号必须逐项核对 |
| 声音 | 环境、物件、机关、章节过渡，音量和循环规则 |
| 来源 | 本地路径、作者或来源、许可／使用范围、用途、版本、待核对项 |

资源验收至少覆盖角色是否正确、花种是否正确、是否有白边、像素是否足够、大小关系是否合理、重要内容是否被遮挡。

### 5.3 动画要解释动作，不掩盖问题

每段关键动效按“触发 → 物件动作 → 状态变化 → 恢复交互”设计。开抽屉、翻信、显影、拉动红线、转场和打开生日信应有各自对应的物理反馈。

环境动效保持克制：纸页微动、灯光轻变、猫狗的小动作、花瓣与风。不使用持续抖屏、无处不在的发光粒子和整页反复浮动来替代质感。

过场支持跳过；跳过时也必须提交同一个完成状态。离开章节后停止该场景的动画与监听，避免重复触发、声音叠加和隐藏场景继续运行。

有声媒体可能受浏览器自动播放策略限制，因此应在玩家点击开始／开启声音时初始化音频，并处理播放失败，不能假设页面载入后音乐必然响起。参考：[MDN自动播放说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)。

## 6. 谜题标准：难在推理，不难在猜作者想法

每个正式机关必须有一张完整设计记录，最少写明：进入条件、可见线索、可用物件、操作、规则、唯一解或等价解、错误反馈、解锁结果、下游用途、三级提示、保存状态和测试步骤。

主线依赖要能画成可检查的有向关系：不能出现A需要B、B又需要A；不能让唯一道具被错误消耗；可选彩蛋不阻断主线。

本轮建议整部作品先围绕八个阶段控制规模，约12—16个有明确作用的主机关，再按试玩情况增加少量可选内容。这是范围建议，不是已确定数量；优先保证每个机关有价值，不为时长灌水。

提示按三级推进：先提示观察范围，再提示物件关系，最后给出具体动作或答案。第三层可以明确解法，不以故意含糊延长卡关时间。

涉及颜色、声音、拖拽或精细观察时，提供另一种可读／可操作线索。角色知识只增加熟悉感，不要求玩家额外查百科才能继续。

## 7. 工程路线：保留职责，不为换技术栈而重写

### 7.1 第一阶段的默认决策

继续使用静态网页交付，保留GitHub Pages适配。不新增账号系统、数据库、排行榜、后台管理或在线模型调用；这些不服务于当前生日游戏目标。

现有内容、谜题、状态与界面的分离原则继续有效。先以单章样板验证场景表现与交互，再决定是否需要引入专门的二维游戏渲染层，不立即整体改为React、Next.js或其他新框架。

若原生实现开始大量重复手写场景生命周期、热区输入、镜头、图层和动画管理，再评估Phaser等二维框架。Phaser官方提供场景系统和统一指针／触屏输入；这说明它是候选工具，不代表迁移已经被批准或能自动提升美术水平。参考：[Scenes](https://docs.phaser.io/phaser/concepts/scenes)、[Input](https://docs.phaser.io/phaser/concepts/input)。

GitHub Pages属于静态托管；本项目的静态交付方向与之匹配。参考：[GitHub Pages说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)。

### 7.2 必须明确的职责边界

- 内容层：章节、对白、道具描述和提示，不处理DOM。
- 规则层：输入状态与动作，输出新状态／结果，保持可单独测试。
- 场景层：展示背景、物件、热点和局部视图，不把答案散落在点击回调里。
- 运行层：物品栏、场景切换、输入锁定、音频、资源加载和清理。
- 存档层：版本、有效值校验、异常数据兜底、迁移和重置确认。
- 展示层：文本、物品栏、提示、设置和响应式布局。

只在样板需要时建立对应文件，不提前创建大量空目录、管理器、插件系统和无用抽象。

### 7.3 优先补的可靠性工作

1. 修复逐文件语法检查；统一版本源。
2. 校验存档中的章节ID、数组成员、顺序合法性、旋转范围和布尔值；不只检查JSON可解析。
3. 关键资源按章预加载，错误提示可以重试；下一章资源失败时不把玩家困在黑屏。
4. 场景切换后释放监听和动效，连续点击只产生一次关键状态变更。
5. 验证 `/smallgame/` 子路径、直接刷新、重新进入和发布版本显示。
6. 新存档与旧存档明确区分；不静默清空用户旧进度。
